```
frontend (Next.js) --cookie--> backend (Express + MongoDB) --X-Internal-Key--> ai-service (FastAPI + LangGraph)
                                                                                 core: domain/ agents/ graph/
                                                                                 ports/  <-implemented by-  adapters/ (Groq, Cloudflare, SearchApi.io, Nominatim)
```

## Five rules the product enforces

1. **No plan without the required fields.** A Trip is planned only when Origin, Destination, Duration, Budget, Party Size and Travel Style are all known. Otherwise the Traveler gets a Clarification that lists what is missing. The rule decides this, not the LLM.
   `ai-service/domain/requirements.py:14` (`find_missing_fields`), applied at `ai-service/agents/understand.py:33` (`find_missing_fields`).
2. **Budget Caps.** A Hotel is recommended only if one night costs at most 50% of the Budget divided by Nights. A Flight is recommended only if its fare is at most 35% of the Budget divided by Party Size, plus a 15% grace margin.
   `ai-service/domain/budget.py:31` (`allows_hotel`), `ai-service/domain/budget.py:34` (`allows_flight`), applied at `ai-service/agents/hotels.py:33` (`allows_hotel`) and `ai-service/agents/flights.py:38` (`allows_flight`).
3. **Planned only when a stay fits the Budget.** If Hotels were found but none fits the nightly cap, VoyAgent does not produce a plan. It asks the Traveler to raise the Budget, shorten the Trip or pick another Destination, and quotes the cheapest stay it found. The Estimated Cost of a plan must also fit the Budget.
   `ai-service/agents/budget_check.py:12` (`hotels_over_budget`), guard at `ai-service/agents/budget_check.py:29` (`is_within_budget`).
4. **No silent Destination swap.** A place with no known Airport Code never falls back to another city's airport. Flights are skipped and the Trip Plan carries a Note that says why.
   `ai-service/domain/airports.py:54` (`airport_code`), `ai-service/agents/flights.py:14` (`origin_code`).
5. **Only the owner can use a Trip.** Reading, continuing or deleting someone else's Trip gives 403, a missing Trip gives 404 and a malformed id gives 400. A `planned` Trip is final and cannot be re-planned (409).
   `backend/src/domain/trip.js:40` (`isOwnedBy`), `backend/src/services/trip.service.js:8` (`findOwnedTrip`).

## Three design decisions

### 1. The LLM sits behind a port the core owns (DIP and the boundary)

- **Where:** `ai-service/ports/llm.py:12` (`LLMPort`), `ai-service/adapters/fallback_llm.py:8` (`FallbackLLM`), wired only in `ai-service/container.py:31` (`FallbackLLM`).
- **Before:** Calling a vendor SDK directly from each LangGraph agent couples high-level planning steps to one Provider, forces edits across every agent when the model or wire format changes, and requires live API keys to test planning rules.
- **Why it changed:** Our LLM setup changed repeatedly during development: we added Cloudflare Workers AI as a fallback behind Groq and switched Groq to schema-constrained JSON output with transient-failure retries (`c1dfda1`). Every change stayed inside `adapters/`. Agents accept an `LLMPort` through constructor injection, so tests pass `FakeLLM` (`ai-service/tests/fakes.py:14` (`FakeLLM`)) with no network access.

### 2. Budget arithmetic moved out of the LLM into one pure module (SRP)

- **Where:** `ai-service/domain/budget.py:11` (`BudgetCaps`), used by `ai-service/agents/budget_check.py:8` (`budget_check`). The final LLM call now only writes prose: `ai-service/agents/compose.py:21` (`TripSummary`).
- **Before:** Relying on the LLM to judge whether prices fit the Budget is non-deterministic, and pushing price caps down into the search adapter (`SearchApiSearch` in `7c02515`) split one money rule across two layers while hiding over-budget stays from Rule 3. Standard floating-point arithmetic also rejected exact boundary fares (such as a ₹4,025 fare against a ₹3,500 + 15% cap).
- **Why it changed:** Money rules must be deterministic, single-sourced, and testable on exact boundary values. Now one pure module owns the shares and uses `Fraction` (`ai-service/domain/budget.py:30` (`Fractions keep`)). Recommendations pass into the Trip Plan unchanged instead of being regenerated by the LLM.

### 3. Trip Status is an explicit state machine (types as design)

- **Where:** `backend/src/domain/trip.js:24` (`nextStatus`), used at `backend/src/services/trip.service.js:44` (`nextStatus`).
- **Before:** Early `backend/src/models/trip.model.js` (`44aa1cb`) allowed the raw strings `clarification_needed | completed | error`. The controller assigned them directly, `error` was never set, a completed Trip could be planned again, and the frontend compared `status === "completed"` by hand. "Completed" also meant "plan ready", which clashes with the travel meaning (flagged in the glossary).
- **Why it changed:** illegal states should be impossible to build, not checked everywhere. `TripStatus` is frozen. Moves are allowed only through a transition table where `planned` is terminal. A Planning Engine outage is now recorded as `planning_failed` so the Traveler can retry the same Trip. All of it is pure code with no Express or Mongoose, tested in `backend/tests/domain/trip.test.js:22` (`a planned Trip never changes`).

## One boundary

**Where core logic stops:** inside `ai-service`, the core is `domain/`, `agents/` and `graph/`. `domain/` imports nothing from LangGraph, LangChain, HTTP clients or settings (`ai-service/domain/__init__.py:1` (`Pure trip rules`)). Agents and the graph depend only on the ports: `ai-service/ports/llm.py:12` (`LLMPort`), `ai-service/ports/search.py:32` (`HotelSearchPort`), `ai-service/ports/search.py:36` (`FlightSearchPort`), `ai-service/ports/geocoder.py:10` (`GeocoderPort`).

**Where the outside world begins:** `adapters/` (Groq, Cloudflare Workers AI, SearchApi.io, plus the cache, fallback and estimate wrappers), `settings.py`, `container.py` and the FastAPI app. Source dependencies point inward: adapters import ports, and the core never imports an adapter. `container.py` is the only file that knows which Providers are plugged in (`ai-service/container.py:34` (`build_engine`)).

The Trip Map reused this boundary. Coordinates come from a new `GeocoderPort`; the free OpenStreetMap Nominatim adapter (`ai-service/adapters/nominatim.py:16` (`NominatimGeocoder`)) keeps Nominatim's one-request-a-second limit and caches answers. The locate step runs after `budget_check`, so only Feasible plans spend lookups (`ai-service/graph/builder.py:49` (`"locate", "compose"`)). It never fails a plan: an outage leaves Coordinates empty and adds a Note. The LLM is never asked for Coordinates, because `coordinates` is hidden from the JSON Schema it sees (`ai-service/schemas/itinerary.py:14` (`SkipJsonSchema`)); invented lat/long would put pins kilometres away.

**What it protects us from:** volatile external Providers. During development we paired Groq with a Cloudflare Workers AI fallback, adjusted Groq wire handling, and added `EstimateSearch` behind SearchApi.io for when the free quota runs out. None of these changes touched a domain rule or a test of a rule.

**Cost:** one interface per Provider kind and one more level of indirection. A boundary is only worth its cost where the outside side is likely to change; here our Providers changed repeatedly, so it paid for itself. The backend uses the same idea for the Planning Engine: `backend/src/clients/aiPlanner.client.js:26` (`requestPlan`) is the only file that knows the ai-service wire format.

## AI use

**Tools and what they were used for**

- **Claude Code (Claude Opus 5.5)** was used to:
  - propose the port plan and the five rules;
  - write each area's tests first and then the code;
  - run live smoke tests against Groq and SearchApi.io, and an end-to-end browser check.

  Every change was made on a feature branch and reviewed by the area's owner before merging.
- **Groq (`openai/gpt-oss-120b`) and Cloudflare Workers AI** are runtime Providers inside the product. They extract the Trip Request and write the Itinerary, the summary and the estimates. They never decide a rule.

**One AI suggestion we rejected:** Claude suggested sending the Budget Caps to SearchApi.io as `price_max` / `max_price`, so that only affordable Hotels and Flights would come back. It was implemented in commit `7c02515`. We rejected it while writing the Planning Engine tests, for two reasons:
- If the Provider filters, an empty result cannot tell "everything is too expensive" from "there is nothing there".
- Rule 3 could then never trigger, because a 50% share plus a 40.25% share is always under 100% of the Budget.

The caps now apply in the core, after the search (commits `f29e15d` test, `36e3006` fix). Over-budget results stay visible, and the Traveler is told the cheapest price we found.
